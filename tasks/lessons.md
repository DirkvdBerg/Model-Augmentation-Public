# Self-Improvement Ruleset

A **ruleset**, not an error log. Add a lesson only if it is (1) **generalizable**, (2) **actionable**
("when X, do Y not Z"), (3) **novel** (else strengthen the existing rule, never append a duplicate).
When a mistake recurs, merge it into the existing rule. When a rule proves its value repeatedly,
consider promoting it to `CLAUDE.md`.

**Two-tier structure.** This file is the ACTIVE ruleset: one line per lesson (trigger + rule), read
every session. The full `Why` / `How to apply` / incident narratives and all dated scope-extensions
live in `archive/lessons-incidents.md`, keyed by the same **slug**. Read the archive only when you
need a rule's backstory. When you add a rule or extend a scope, put the narrative in the archive and
the one-liner here — keep this file tight.

## Interaction & workflow discipline
- **answer-before-code** — On a question, shared context, or problem: respond in text first; call no tools and write no code until the user explicitly confirms direction. "Let me implement" then editing in the same turn is a violation. "Plan approved" means discuss step 1, not build everything at once. "I want to run X on the web / in tool Y" means WRITE THE INPUT for that tool, not run a local equivalent.
- **log-lesson-on-correction** — On any correction/rejection/redo, apply the 3-criteria gate and update this file BEFORE resuming execution. Do not defer; corrections get forgotten once work resumes.
- **modify-only-what-was-asked** — Edit only the files, and the parts within a file, explicitly requested. Flag stale/inconsistent siblings in text and ask; a previously-declined offer is not re-authorized by a narrower later request. If the message also has a discussion request, give the discussion first, before any file work.
- **use-users-exact-term** — Implement the exact concept/procedure/metric/file/script the user named; never silently substitute a related or "more correct" sibling. If a named file/artifact isn't found, say so and ask. Substitution needs a RISK flag in chat and agreement. Project-documented mechanism names and folder/placement conventions count as the user's terms. "Don't touch <file>" = stop all read and write on it.
- **commit-after-direction-given** — Once the user has confirmed a direction (especially if repeatedly), STOP re-asking for confirmation and execute. Re-requesting approval you already hold reads as not listening and burns trust fast. If earlier tool uses were rejected, the fix is a correct artifact aligned to the user's STATED preference (their tool, their data, their framing), not another clarifying question. If the user repeats a point, you already missed it once: adopt it, do not re-litigate it. Do not contradict a constraint your own analysis established ([[dont-contradict-own-research]]).
- **one-recommendation** — On "what next", give exactly ONE concrete action with rationale and stop; no option menus/tables unless asked. Do not write a new doc as a substitute for the next runnable step or primary-read.
- **summary-after-long-answer** — Close any long analytical answer with a short bottom-line summary: conclusion, what's proposed, next action.
- **dont-kill-inprogress-work** — Before a Stop-Process / rm / relaunch that discards running work, state your interpretation and get confirmation, unless the user explicitly said to stop it. A running job is cheap to finish, expensive to recreate.
- **no-command-referencing-uncreated-artifacts** — Before handing over a runnable command/prompt/handoff, create every artifact it references (verify each exists) or label it "DRAFT — not runnable until I create <list>". Assume the user runs it verbatim immediately.
- **removing-a-rule-needs-justification** — A proposed edit that deletes/weakens a user-authored rule (CLAUDE.md, lessons, settings) must, in the same message, justify it, check the intent still holds, and offer a softened intent-preserving rewrite (default: soften, not delete). Flag the conflict of interest when it constrains your own behavior.

## Assert nothing without evidence
- **dont-contradict-own-research** — When your own research/analysis has established a hard requirement (e.g. "a U0=0 multisine has no power at DC, so testing for a static/DC component REQUIRES specific DC-exciting input: step/ramp/low-frequency"), every later proposed method must satisfy it. Do NOT retreat to a convenient approach that violates your own finding (reusing DC-blind multisine data to test for a DC/non-zero-mean component cannot work, by that finding). The research's conclusion is BINDING on the plan; when the user pushes back, re-derive from the established constraint rather than abandoning it. Before proposing a data source, check it against the identifiability constraint your own analysis produced.
- **no-cost-claims-without-measurement** — Never label a run/config "cheap/fast/affordable/~Nx faster" without a measured number (a prior run's sec/batch or MB) or one the user gave. BPTT horizon (nf) is expensive at every scale here. If cost matters, quote a measured number or ask what is runnable on their hardware.
- **no-failure-cause-without-run-evidence** — Do not attribute a run's failure to a cause without direct evidence from THAT run's own log/sacct/config; confirm any shared script/config actually produced the failure. MANDATORY first step reading any run log: read its printed Configuration block (lr, flags, routing) and check it against the intended config — deployed copies lag local edits.
- **search-before-flagging-unknown** — Before writing "assumption/unknown/TBC" or asking for a system property, grep the sources already read this session, including code comments and variable-definition lines. Only flag what is genuinely absent. Before flagging a COMPONENT's behavior as an unexplained issue "worth investigating", read THAT component's own source/docstring first — it may already characterize it (telica_controller.py's docstring documents the exact per-axis amplitude offsets 1.16/1.33/3.55 and their cause that I "discovered" from a plot and called new).
- **confirm-in-loaded-model** — Do not assert a packaged model (.slx) contains a block/param from its raw serialized XML; .slx can carry orphaned subsystem XML not wired into the live graph. Confirm via `load_system` + `find_system` (LookUnderMasks/FollowLinks). `find_system` is the source of truth.
- **quote-from-the-producing-script** — Before quoting a data-derived parameter, confirm the script you read is the one that actually `save`s the data file the pipeline consumes; repos have prototype/generator twins with different values for the same variable. If two disagree, flag it rather than pick one.
- **measure-on-target-not-proxy** — A physical mechanism is a HYPOTHESIS until measured on the exact deliverable object (e.g. the trained ANN), never a proxy (baseline-only, full-truth, untrained). Label inferred mechanisms as unmeasured and surface any data that does NOT fit the narrative.
- **causal-claim-needs-intervention-not-observation** — Do not headline an INFERRED cause as settled ("the cause is X"); a caveat later does not cancel an overclaimed headline. An inferred mechanism stays a hypothesis until an INTERVENTION isolates it. To test a TRAINING-TIME cause (does encoder-init error cause the learned DC?), TRAIN under the intervened condition (train from true x0), do NOT just EVALUATE the already-trained model under it: a trained-in artifact (a DC baked into the weights) appears under ANY evaluation init and tests nothing. When the user offers such a control, run it before defending the inference; if it falsifies the story, drop the story.

## Control-engineering reasoning
- **coords-driven-by-data** — Do not argue one representation is physically superior when both describe the same system; the data's coordinate frame decides. Model and data must match.
- **theory-context-must-match** — Before `# THEORY:` or citing a literature rule as a recommendation, confirm it was derived for the SAME identification method AND noise setting. Noise-motivated arguments (SNR, period/realization averaging, BLA variance) do not transfer to noiseless simulation. Flag the mismatch or omit.
- **empirical-quantities-from-data** — In an empirical/real-data phase, derive every verification quantity (time constant, fs, threshold, noise floor) from the observed data, never from model matrices/eigenvalues or model-generated synthetic data. Non-negotiable; violated repeatedly.
- **threshold-defensibility** — Weigh a proposed acceptance threshold by defensibility (model-free, standard in the field, transfers to real data where no oracle exists), not only numerical validity. The noise floor beats an oracle-model floor even when numerically equal.
- **degenerate-id-has-many-explanations** — When a fit determines a lumped quantity with more than one physical cause (mass vs force scale), present ALL physically-consistent interpretations, state the data cannot decide, and name the external reference that would. Never call one "impossible"; recovered ≠ model nominal may mean the model is wrong for THIS system. A residual PLOT identifies the error CLASS (force/DC vs fast dynamics), not the mechanism; a residual-vs-velocity loop is not clean friction evidence (phase lag also traces a loop).
- **classify-not-learning-from-loss-shape** — On "not learning", read the TRAINING loss first: rising/bouncing = lr overshoot → lower lr; flat/monotone = step/data starvation → add steps/data. Optimal lr is routing-dependent (K=0 X/Y routing needs ~100x smaller lr than Theta's); re-tune lr per configuration before blaming the data.
- **simplest-sufficient-cause-first** — Explain behavior with the simplest cause that fully accounts for it (does the model MATCH the data at convergence? then no force error, no drift — done); invoke elaborate mechanisms (windowing, conditioning) only as clearly-labelled secondary modifiers.
- **control-condition-must-be-clean** — In an A-vs-B comparison, confirm the control/baseline is well-behaved (converges, bounded, beats its init) BEFORE attributing an effect to the treatment. If the control also misbehaves, fix the setup and re-run; do not log the decision off a broken control.
- **attribute-to-the-isolated-block** — An input-output check that BYPASSES the plant model (feed MEASURED error into the controller, compare to LOGGED output) isolates the CONTROLLER path; a mismatch there is a controller/control-path model gap (e.g. an unmodeled decoupling transform), NOT the plant. Name which sub-model a check actually exercises before attributing the error; don't lump a controller-path mismatch under "plant model".
- **established-metric-wins** — A fresh/smoke diagnostic (few windows, a different reduction like endpoint-|err| vs RMS) does not override the established metric (training val nf-RMS) until run in full with the SAME reduction. Match the reduction before concluding.
- **drift-by-position-envelope** — Test free-integrator (K=0) drift as position-ENVELOPE growth across windows (RMS|q| late/earlier ~1 bounded, >~1.2 drifting), never via a slope/velocity proxy: a bounded lightly-damped resonator trips a slope/v-ratio test. Confirm a sustained-DC control yields envelope-ratio clearly >1.
- **measurement-noise-post-hoc** — Add measurement noise post-hoc to the measured output at the working rate (Jan's SNR convention). Never inject it inside the closed loop, never add independent noise to u. It is band-limited by construction and does not alias ([[measurement-noise-post-hoc]] keeps the anti-alias filter real-data-only).
- **trace-state-reconstruction** — Before claiming how noise reaches unmeasured states, read the encoder/observer forward pass. Position-only input does NOT give clean velocities: `x0 = W_y·yhist + W_u·uhist` (W_y = A^n·pinv(O)) differentiates the position window and AMPLIFIES noise into velocity error (gentler than 2-point FD, non-zero, worst on low-signal channels like yaw velocity).
- **sampling-rate-two-requirements** — A passing downsampling validation confirms only state-transition accuracy, NOT encoder-init quality; verify BOTH before choosing a rate. Derive the encoder-init threshold from the native-rate result, not an arbitrary number.

## Augmentation design (no-drift / passivity thread)
- **velocity-loss-is-last-resort** — Velocity/accel/force-domain training loss (fix C) is an explicit LAST RESORT (supervisor). List position-based fixes first, never let literature convergence (DIDIM/Ljung/Tustin) elevate it, label it "LAST RESORT" everywhere, adopt only on explicit go-ahead. Tustin-Net is a STRUCTURAL integrator-factoring architecture (keeps a position loss), NOT the velocity loss; do not conflate.
- **xy-routing-is-hard-constraint** — Never propose or default to Theta-only routing as a fix or fallback (D-103): X and Y must stay in the ANN routing (coupling is uncapturable without them). Solve K=0 drift WITH X/Y kept; Theta-only is a controlled diagnostic baseline only, never the deliverable.
- **verify-interconnect-routing** — Before proposing an I/O constraint on a block, read the interconnect wiring (`connect_block_signals`, nz/nw, selection matrices) to confirm what it actually receives. Here the ANN reads the FULL state x + u; velocities are encoder-reconstructed ([[trace-state-reconstruction]]). Phrase constraints as selections on the real indices. Output-route (D-103: X/Y force OUT) is distinct from input-read; never phrase input-scoping as dropping the output route.
- **structural-gaps-fixed-structurally** — Do not patch a missing GUARANTEE (bounded position, stability, passivity) with an ad-hoc numerical regularizer (R+εI, weight decay, clip) — that is a HEURISTIC that only masks the mode. Identify the structural property that yields the guarantee by construction (NI/free-body bounds a free-integrator POSITION; plain passivity bounds only velocity).
- **constrain-output-not-input** — Buy a structural property from the ANN's OUTPUT parametrization (telescoping/bounded-impulse, a constraint on dF/dq), never by dropping states from its INPUT. Keep the full-state input `["x","u"]` (preserves Y-scheduling, cogging); input-amputation is the forbidden velocity-domain move in disguise.
- **steering-not-blunt-bound** — Frame augmentation constraints as STEERING learning within a knowable subspace (like orthogonal projection: steer away from the FP-model subspace, or into the F·v≤0 half-space), not as a blunt output cap. The steering target must be knowable WITHOUT the true dynamics (physics subspace / power sign OK; the residual MEAN is not knowable — why the DC/mean penalty was demoted). Impulse-based no-drift constraints suppress friction exactly like the mean penalty (friction carries net impulse); only power-sign (F·v) distinguishes drift from friction.
- **unknown-system-no-class-restriction** — For a real-data deliverable with unknown true dynamics, never make a class-restricting HARD constraint (passivity, dissipativity, net-impulse, contraction, NI-by-construction) the deliverable: any forbidden class might BE the true residual and is unverifiable. Full expressivity XOR a for-all-weights no-drift guarantee are logically incompatible. No-drift must come from the ESTIMATOR: training conditioning (multiple shooting + continuity) + regularizing only the unexcited/null direction (orthogonal projection). No-drift is then training-CONDITIONAL, not guaranteed — the price of expressivity.
- **prove-overconstraint-dont-multiply-methods** — After 2-3 failed solutions to the same spec with the user unconvinced, stop generating methods: PROVE the requirement set is incompatible (expressivity XOR guarantee → two families, each dropping one requirement), then relax the requirement that is impossible AND unnecessary, or question the metric (open-loop free-run vs closed-loop deployment). Before citing any "proven mundane X" as an untried fallback, grep the run/Optuna table to confirm it was not already tested on THIS problem (multiple shooting was, and failed on the augmentation: Optuna 69399 best = epoch 0).

## Code & implementation discipline
- **fix-at-the-wrong-assumption** — Fix a bug in the component that made the wrong assumption, not in its callers or the data pipeline. If a class misreads a well-defined framework convention, fix the class, not the interface around it.
- **instrument-deepSI-at-the-called-method** — To probe/inject inside a deepSI interconnect forward (per-step gradient, output bias), do NOT use nn.Module forward hooks: the interconnect calls `block.forward(z)` DIRECTLY (`interconnect.py:92`), bypassing `__call__`, so hooks never fire during training (symptom: an injected-bias `.grad` stays None/NaN while a separate `block(z)` probe works). Patch the method the framework actually calls (`ann.forward`). deepSI `checkpoint_save_system` pickles the whole system (`torch.save(self.__dict__)`), so any injected closure/hook/attribute must be picklable, OR no-op `fit_sys.checkpoint_save_system` for the run (the end-of-fit `_best` reload is wrapped in `try/except FileNotFoundError`, `interconnect.py:717`, so skipping saves is safe). For per-optimizer-step logging, patch `torch.optim.Adam.step` (deepSI creates `fit_sys.optimizer=Adam` inside `fit()` and calls `optimizer.step(closure)`). Confirm the model's state ORDER from source (`model.py:31` = `[X,Theta,Y,dX,dTheta,dY,delta_a,vdelta_a]`, NOT the MATLAB `[X,Th,Y,da,...]`) and map ANN output columns via `cfg.ann_route_ix`, not the orth penalty's `route_cols`.
- **preserve-reference-skeleton** — When adapting a reference script (Jan's ECC-2025), keep its section order, naming, and structure; make minimal changes; append new sections after the original's final block. Do not rewrite from scratch — that makes the diff invisible.
- **verify-ownership-before-added-marker** — Before an `@added` marker in `model_augmentation/`, confirm via `git show 6d69f6b:...` that the symbol did NOT exist in Jan's original commit. Do not rely on the current file state.
- **check-all-pipelines-first** — Before declaring a change necessary, grep ALL three pipelines (`model_augmentation/`, `lpv_lfr_baseline/`, `real-data-verification/`) for an existing implementation; capabilities often already exist in a sibling.
- **replicate-compilation-on-hot-path** — Re-implementing a baseline hot loop (rk4_step/simulate/BPTT forward) must reuse its compile wrap (`torch.compile(backend=COMPILE_BACKEND, fullgraph=True)`, jit.script fallback), not run eager. Import `_USE_COMPILE`/`COMPILE_BACKEND` from `lfr_simulate`.
- **one-config-surface** — Every user-tunable parameter must be settable from one block at the top of the entry file, with one source of truth; no typed config object PLUS a separate hand-authored hp dict. Derive any dict view from the object (`cfg.hp`).
- **effect-in-consuming-representation** — Express a new physical effect (friction) in the CONSUMING pipeline's representation, checked first (Python LPV-LFR simulate: M/C/K matrices + the LFR z/w Delta path for a static nonlinearity), not a convenient MATLAB ode45 wrapper. Telica/real-data extensions live in `real-data-verification/` and OVERRIDE the baseline via patching; do NOT edit `lpv_lfr_baseline/` core in place.
- **deliverable-is-recovered-model** — When adding a term meant to be RECOVERED from data, keep making it trainable and wiring it into the recovery entry point as the primary track. Fixed-parameter open-loop what-ifs are secondary and can mislead (a fixed, different-machine value is far from what the data would fit).
- **identify-the-missing-scalar** — When a known model has one unknown scalar and calibration data exists, identify it by least squares (`scale = <h, MF30>/<h, h>`); do not replace the model with a static-gain/RMS proxy that removes the frequency shaping.
- **fix-not-delivered-until-deployed** — A fix the user runs elsewhere (cluster) exists only locally until re-synced: say so prominently and give a one-line verify command (grep the removed line). On a returning complaint, establish WHICH copy ran before re-diagnosing. Uncommitted changes make git-based sync silently miss the fix.
- **no-scaffolding-in-experiment-scripts** — Keep operational hooks (SMOKE_TEST env modes, preflight gates, rehearsal switches) out of experiment scripts, and do not remove user-visible output (tqdm, prints) as "noise". Approval of a goal or a tool's value is not approval of the artifact; on hesitation ("not sure I like this"), remove without defending. For any new tool >~100 lines, show the skeleton first. STICKY: every gantry training/search script MUST print `[nf-probe] train nf-RMS / val nf-RMS` each epoch (reinstall the probe per chunk; plain `train_model` does not install it).
- **validate-with-actual-pipeline** — Validate a pipeline parameter with the model the pipeline actually uses (LPV nonlinear, not an LTI proxy) and data covering the operating range. A reference/oracle model must run at the SAME sampling rate and `up_sample` as what it is benchmarked against (only a standalone correctness diagnostic may crank them — re-verify at pipeline settings after). Test inputs must come from the actual producer (call it, or read its contract), never fabricated to the consumer's own assumption.

## Verification & testing
- **test-zero-mean-properly** — Separate the DESCRIPTIVE question ("is this recorded signal/correction zero-mean?", answerable on EXISTING data: compute the signal, run the tests) from the INFERENTIAL one ("does the system/baseline have a static DC deficiency in general?", which needs DC-exciting data because a U0=0 multisine is DC-blind). Answer the descriptive question asked on the data we have; state DC-blindness as a CAVEAT on the result, do NOT escalate to generating new excitation unless the user asks the inferential question. The correction the ANN must learn is defined on the training records, so the training distribution is the correct place to test it. To decide if a signal/residual/correction is zero-mean or DC-free, never use a `|mean|/std` (or `|mean|/rms`) ratio or eyeball "park vs ramp" — neither is a hypothesis test. Do: (1) classify stationarity FIRST (KPSS null=trend-stationary + ADF null=unit-root) — on a K=0 integrator axis the raw position mean is ill-posed (nonstationary), so test the stationary quantity (velocity, or the one-step model residual), and "deterministic park vs stochastic drift" IS the unit-root question; (2) test the mean with a HAC / Newey-West long-run-variance t-stat, because under autocorrelation (150 Hz ripple + slow trend) `std/sqrt(N)` is wildly optimistic and the true sample-mean variance is `2pi*S(0)/N` (spectral density at f=0); (3) the required correction is literally the baseline's one-step RESIDUAL, so "does the system demand a non-zero-mean correction" = the standard SysID residual test: zero-mean (HAC t) + whiteness (Ljung-Box); (4) two reframes that must accompany any verdict: a multisine with U0=0 carries ZERO information about the static/DC gain (a "zero-mean" finding is partly guaranteed by the DC-free experiment, not the physics — identifiability), and a nonlinear/LPV plant rectifies zero-mean input into a genuine 2nd-order Volterra DC, so "zero-mean input" never implies "zero-mean output". (5) MIRROR BLINDNESS in DC-excitation design: each waveform probes only its OWN DC mechanism. A U0=0 multisine is blind to STATIC-GAIN DC; a pure sustained/step input is blind to the AC-driven 2nd-order RECTIFICATION DC (it drives the plant to a nonlinear static equilibrium — no oscillation to rectify, so any resonator/MSD state relaxes to 0). At steady state qddot=0, so the mass matrix M — often the ONLY thing differing between two models — drops out of C*qdot+K*q=F; a static open-loop same-input test then confirms only "no static-gain difference" (frequently predetermined ~0 by that algebra), NEVER the full "system carries no DC the baseline lacks". The rectification DC that SURVIVES a truth-minus-baseline difference (here the MSD delta_a term) needs an AC component at the resonance to appear. To test BOTH mechanisms in one run, drive an offset PLUS an AC burst. Before calling a DC/excitation test "in line with the theory", name which DC mechanism the waveform actually excites and confirm it is the one the theory flags as real. Tools: statsmodels `kpss`, `adfuller`, `acorr_ljungbox`, HAC via `cov_type='HAC'`.
- **verify-nonlinear-mechanism-fully** — To attribute a measured effect to a specific nonlinear mechanism (quadratic / Volterra rectification), do three things or you may measure a look-alike: (1) excite the STATE the mechanism depends on and PROVE it moved (report its amplitude/RMS — a driven axis that barely reaches the state gives a false "negligible"; here only the Y drive moved delta_a, RMS 1.67e-5, vs ~1e-11 on X); (2) OBSERVE the channel where the nonlinear term physically lives (its home coordinate: the delta_a^2 term sits in the Theta inertia M(2,2), so read Theta, not the driven axis); (3) verify the expected SCALING (rectification DC ~ <state^2>, so it must track amplitude^2: measured B[Theta]=3.1e-10 matched <delta_a^2>=(1.67e-5)^2=2.8e-10 to ~10%). Matching magnitude AND scaling confirms the mechanism; a same-order number on a drive that does NOT excite the state is a DIFFERENT effect (here the L0 / mass-split static mass-matrix asymmetry), not the mechanism.
- **value-check-not-just-shape** — For any output touching a coordinate transform (P-transform, rotation, selection, normalization), add a value-correctness check against an independently-computed reference. A passing shape check is not evidence the coordinates are right.
- **seed-must-reach-model-build** — Before trusting a "multi-seed" result, PROVE the seed actually varied the model: check that two seeds' outputs differ (byte-identical trajectories / identical step-0 loss = the seed never propagated). In this codebase `demo_common.build_pipeline` reseeds np/torch from `cfg.seed` (demo_common.py:61,78), so setting only the global `np.random.seed`/`torch.manual_seed` in a caller does NOTHING if you then pass the shared `CFG` — every "seed" rebuilds the identical model. Vary the seed AT the config: `dataclasses.replace(CFG, seed=seed)` (RunConfig is frozen; `hp` is a computed property so replace is safe) and pass it into `build_pipeline(cfg=...)`. A controlled A-vs-B contrast at one fixed init (e.g. Adam vs SGD) is still valid, but do not claim seed-robustness from runs that share an init.
- **check-the-run-log-before-concluding** — Before presenting a run as new evidence, a confirmation, or a candidate fix, search the D-090 run log (`docs/gantry-augmentation-problem-log.md` §12) for a prior run that already tested the same knob — even when the run itself is clean. The nf=400→800 truncation sweep was reported as a fresh "source confirmed / longer windows mitigate" result while the SAME table already had the independent nf-sweep (SLURM 71013, nf={800..3200}) showing the dY-DC present on all checkpoints ~1/nf with the drift NOT fixed at any nf. The new point was corroboration (it sits on the 1/nf law), and the prior run had ALREADY refuted "longer windows as a fix" — so framing longer windows as a "complementary fix" contradicted logged data. A clean result interpreted without its prior context can invert the conclusion (diagnostic-confirmation vs candidate-fix). Grep the log for the knob (`nf`, the routing, the optimizer) and reconcile the numbers before writing the verdict.
- **verify-knob-moves-the-target-before-running** — Before spending a training run on an intervention, prove the knob actually moves the quantity the hypothesis is about, in the regime that matters, WITHOUT a fit-wrecking side effect. The pole-perturbation (add X/Y stiffness to move the K=0 pole z=1→z=1-δ and test the λ→1 truncated-BPTT-bias source) failed this: for a mass-damper the position-mode decay rate is -c/(2m) (set by damping/mass) and is ~INDEPENDENT of stiffness — so stiffness barely moved the within-window decay (~3% over a 0.1 s window; natural timescale ~3 s) while the restoring force K·q (q~0.3 m → ~300 N) wrecked the baseline fit (sim-RMS 1.6e-4→0.106, 650x). A 30-min run produced an INCONCLUSIVE, confounded result that a 1-minute pole/eigenvalue + force-magnitude calc predicted. Do the closed-form check first: (1) does the knob move the target quantity (here: compute the pole shift — it didn't, decay is damping-limited), and (2) does it introduce a dominant confound (here: K·q force). If either fails, redesign the knob (a damping-limited decay needs a DAMPING or horizon knob, not stiffness) or pick the cleaner test (the truncation-length sweep settled the same question). Generalizes the DC-excitation `test-zero-mean-properly` clause-5 blind-spot rule to ANY interventional knob.
- **diagnose-by-reading-code** — Diagnose a test/smoke failure from the traceback + 1-2 targeted file reads, not repeated slow test runs. Run a second command only to directly confirm/falsify the hypothesis with a fast result.
- **diagnostic-independent-and-minimal** — A diagnostic must run WITHOUT the completed pipeline it verifies (construct the component from scratch) and use the MINIMAL call that tests that component (call the encoder on I/O windows; do not route through `apply_experiment`/full simulation).
- **justify-implications-for-the-construction** — Before "X implies Y" or "iff" in a derivation, show why it holds for THIS specific construction (e.g. well-posed iff M(Y) invertible only because D_zw encodes M(Y)^{-1}); do not assert it as a general theorem unless it is one.

## Writing, documents & figures
- **no-em-dashes** — Never use em-dashes in any output: not the Unicode —, not the LaTeX `---`, not `--` as a substitute. Applies to prose, LaTeX, code comments, and TEXT INSIDE FIGURES (legends, titles, captions, annotations). Existing "--" in a touched file is not license to add more; write new text clean and flag the old.
- **reference-docs-describe-what-exists** — A reference/summary doc contains only what is in the source (structure, content, relationships); interpretation, next steps, and conversion implications belong in `docs/decisions.md` or task plans, not the reference.
- **diagnostic-figures-are-falsifiable** — Save diagnostic data (JSON/CSV) + figures under `simulations/<system>/diagnostics/`, not `scripts/`. Design each plot as a hypothesis test (prediction vs independent measurement + quantified deviation); never assert the conclusion in the title. FULL-SHOW is the default: enumerate the complete member set (all states, both frames, positions AND velocities; all force/velocity channels in their own units) in the PROPOSAL, not just the built PNG; one physical state per panel (never overlay different states/units on one axis — split into more figures); ≤3 SAME-quantity comparison curves per panel; short labels; scientific-notation y-axes; show the absolute trajectory reference separately from baseline-error; confirm the frame (stage vs logical, P-transform) before any per-channel claim; do a pixel-level visual inspection for overlap/clipping before delivery; disclose any channel selection ON the figure.
