# Self-Improvement Ruleset

A **ruleset**, not an error log. Add a lesson only if it is (1) **generalizable**, (2) **actionable**
("when X, do Y not Z"), (3) **novel** (else strengthen the existing rule, never append a duplicate).
When a mistake recurs, merge it into the existing rule. When a rule proves its value repeatedly,
consider promoting it to `CLAUDE.md`.

**Two-tier structure.** This file is the ACTIVE ruleset: one line per lesson (trigger + rule), read
every session. The full `Why` / `How to apply` / incident narratives and all dated scope-extensions
live in `archive/lessons-incidents.md`, keyed by the same **slug**. Read the archive only when you
need a rule's backstory. When you add a rule or extend a scope, put the narrative in the archive and
the one-liner here — keep this file tight.

## Interaction & workflow discipline
- **answer-before-code** — On a question, shared context, or problem: respond in text first; call no tools and write no code until the user explicitly confirms direction. "Let me implement" then editing in the same turn is a violation. "Plan approved" means discuss step 1, not build everything at once. "I want to run X on the web / in tool Y" means WRITE THE INPUT for that tool, not run a local equivalent.
- **log-lesson-on-correction** — On any correction/rejection/redo, apply the 3-criteria gate and update this file BEFORE resuming execution. Do not defer; corrections get forgotten once work resumes.
- **modify-only-what-was-asked** — Edit only the files, and the parts within a file, explicitly requested. Flag stale/inconsistent siblings in text and ask; a previously-declined offer is not re-authorized by a narrower later request. If the message also has a discussion request, give the discussion first, before any file work.
- **use-users-exact-term** — Implement the exact concept/procedure/metric/file/script the user named; never silently substitute a related or "more correct" sibling. If a named file/artifact isn't found, say so and ask. Substitution needs a RISK flag in chat and agreement. Project-documented mechanism names and folder/placement conventions count as the user's terms. "Don't touch <file>" = stop all read and write on it. NAMED STRUCTURAL METHOD: when the user names a method that is WRITTEN DOWN in a repo spec ("Roland's velocity routing", "the bounded-impulse block"), GREP FOR AND READ THE SPEC before coding/running it, and implement that EXACT structure -- a plausible same-name interpretation can INVERT the result. Incident 2026-07-24: I ran "velocity routing" as raw additive ANN output on the velocity rows (Sum w unbounded -> drifts), but the written method (`dissipative-block-spec.md` §2, R3/Route-A) is the TELESCOPING bounded-impulse force `F_xy,k = phi(z_k) - phi(z_{k-1})`, phi=tanh(net), whose cumulative impulse telescopes to `phi(z_N)-phi(z_0)` = BOUNDED by construction -> drift-bounded (opposite conclusion). Testing the wrong structure produced a wrong "velocity routing doesn't fix it" verdict. NAMED CONTRIBUTION MECHANISM, NOT A HAND-ROLLED PROXY (2026-07-24): the thesis's CORE scientific contribution is the Gyorok ORTHOGONAL PROJECTION regularizer (`Pi=QQ^T` from `SVD(Phi)`, `Phi=df/dtheta`; penalty `beta||Pi.f_ANN||^2`), which ALREADY EXISTS in the codebase (`build_orth_penalty`/`fit_sys.orth_penalty`, `CFG.orth_beta`/`orth_observe`) and which the plan (data-silent-regularization-concept §3) frames Layer 2 as a RE-AIM of (same operator, target subspace changed from FP-spanned to the measured near-DC/joint-DC direction). I instead hand-rolled a window-MEAN near-DC penalty that captures only the SPIRIT -- the user caught this ("you're not working on the orthogonality part?"). RULE: when a step is documented as "re-aim / extend THE <named mechanism>" and that mechanism has real machinery, ADAPT the actual operator (grep `orth_penalty`, read it, re-aim its target subspace), do not substitute a plausible proxy. SECOND FAILURE MODE: do not tunnel on a SECONDARY property (no-drift/R4) with home-grown code while the PRIMARY contribution goes untouched. SCOPE CORRECTION (2026-07-24, user: "you totally misinterpret, the orthogonality is for JOINT ESTIMATION"): the Gyorok orthogonal projection's PURPOSE is JOINT ESTIMATION -- keeping the physical parameters identifiable/interpretable while theta and the ANN are estimated TOGETHER, i.e. stopping the ANN from absorbing/negating baseline dynamics. It is NOT a drift cure, and R4/no-drift is NOT one of its jobs. So: never write "the deliverable is the projection, not no-drift"; never fold drift work under it; never describe a drift task as "making the projection operator work" (I did all three in one message). The speculative "re-aim the projection at the measured drift direction" (data-silent-regularization-concept) is a SEPARATE extension that was TESTED AND FAILED (step4: rank-1 pin dodged, beta saturates under Adam) -- do not resurrect it as the contribution. Drift fixes and the joint-estimation projection are two INDEPENDENT workstreams; name which one a task serves before starting it, and keep the projection's own validation (does joint estimation recover the physical parameters without negation) separate from any drift metric.
- **autonomous-continue-past-ask-headline** — In an autonomous "reevaluate and continue without me" session, do NOT halt just because the HEADLINE next step is a STOP/ASK (e.g. production training). Reevaluate for the cheapest autonomous sub-step that DE-RISKS or fills the highest-value open cell before deferring — the guardrail forbids the expensive/irreversible action, not all progress. If the mission doc itself carves out cheap probes ("gaps you may design cheap tests for", "treat as ASK only if it needs production epochs"), those are IN-SCOPE: design, smoke, and run one. Only stop when every remaining step genuinely trips a guardrail. The single most valuable probe is usually the one testing the WEAKEST-EVIDENCED cell of the promoted candidate (an argued-but-undemonstrated "pass"), not re-confirming a strong one. Incident 2026-07-24: after TASK 1-4 I parked on "green-light the real-data test" when the handoff explicitly permitted a cheap injected-friction/with-MSD R2 probe (non-production) that fills R2 — the biggest open gap and the estimator route's only argued-not-shown cell — autonomously. ENUMERATED-GATES-ARE-THE-ONLY-STOPS (2026-07-24): when a mission spells out its ASK-gates as an explicit list AND says "operate autonomously, only stop at an ASK-gate", ONLY those listed gates halt the loop. A local "show me X before running / before you do Y" is NOT a new ASK-gate — satisfy it by SHOWING X in the same turn (present the plan/skeleton/artifact in the transcript) and then CONTINUE to the run; do not park waiting for a reply the away user cannot give. Inventing an unlisted stop (I treated "show me the harness skeleton before running" as a hard halt and waited) directly defeats the autonomous mandate the same prompt set. If a soft "show me" and the autonomous directive conflict, the enumerated gate list wins. RECURRED SAME SESSION: do NOT checkpoint at every step/sub-step BOUNDARY either ("step 1 done, proceed to step 2?") -- finishing a build step is NOT an ASK-gate; roll straight into the next step and only surface to REPORT progress, never to request permission you already hold. The user being PRESENT/watching is not a reason to pause; they will interrupt if they want to steer. Two "are you working on it / just do it" nudges in a row = I am pausing too often; advance continuously. RECURRED 3x: do NOT emit a per-step "here is what I found, launching the next" message that reads as a checkpoint -- BATCH consecutive steps within a turn and surface ONE CONSOLIDATED report only after several steps complete or at a real ASK-gate. The user REJECTING a tool call to type "don't wait for my responses to progress through all these steps" means PROCEED (re-issue the work and keep going), it is not a halt on that step's content. Chain step->assess->next-step autonomously; background-run completion notifications are the pacing signal, not user replies. RECURRED 4x (2026-07-25): a PRE-DECLARED re-plan branch firing is the LEAST valid reason to stop -- the branch table exists precisely so the re-plan needs no approval. I measured the T0.1 control, saw it trip handoff 5.3's "noise-dominated rig" trigger, and closed with "want me to proceed, or look at the numbers first?" -- the user had to reply "can we continue autonomously". When a mission doc pre-declares the branch for an outcome, APPLYING it is the autonomous path; report the branch you took in the same turn you take it, never ask which one to take.
- **score-the-metric-the-user-is-actually-failing-on** — Before running ANY diagnostic campaign, state the user's complaint in terms of a MEASURED QUANTITY and check that the campaign scores that quantity. Inheriting the metric from a handoff doc, a README or a previous session is not the same as checking it. Incident 2026-07-25: I ran D1 to D7 scoring **R4 free-run drift** because the campaign folder was built around drift, while the user's actual problem was **R2**: the ANN does not learn and the trained model is WORSE than the encoder initialisation. The relevant number was in hand the whole time and never highlighted: in the perfect-match null the ANN-off loss is `L(0) = 8.848e-13`, training jumps to `3.83e-12` (4.3x worse) by step 20 and is still `9.09e-13` at step 350, i.e. training is net destructive on the metric it optimises, for hundreds of steps, from an initialisation that is already exactly optimal. The user: "So in that case wtf are you testing??" Diagnose the complaint, not the folder. RECURRED 2026-07-26 as the ACCEPTANCE CRITERION rather than the metric: I pre-registered a run whose readings were "does the ANN learn the absorber" plus a sim-RMS improvement, and the user corrected: "this is not the issue for now: ANN learned the absorber. we want the ANN to improve it AND most importantly dont worsen the initializaiton". RULE: the acceptance criterion is **two ranked gates against the EPOCH-0 (initialisation) value, not against a physical target**: (G1, primary) training must not DEGRADE the init -- `max_epochs(metric) <= ~1x epoch-0`; (G2, secondary) some epoch must BEAT it -- `min_epochs(metric) < epoch-0`. G1 outranks G2: a run that learns nothing but holds the init is a PASS on the thing that is currently broken, because the present failure is that training is NET DESTRUCTIVE (best checkpoint = epoch 0, sim-RMS 8.0e-05 -> 1.9e-03, 24x worse). Never rank a "did it learn the physics" reading above "did it avoid wrecking the initialisation", and never state a run's verdict against an absolute floor when the user's complaint is stated relative to epoch 0.
- **short-answers-and-hold-the-agreed-scope** — Default to a FEW LINES. Long structured answers with headers and tables are for a deliverable the user asked for (a results doc, a written conclusion), never for a conversational reply. Every reply re-explaining context the user already has is waste they pay for. And once a research or work scope is agreed, do not re-open it, re-frame it, or substitute an adjacent workstream: execute the agreed scope. Incident 2026-07-25: the drift scope was clear (the objective-mismatch question, multiple shooting versus windowed BPTT on a marginally stable plant, the only remedy family my own analysis left standing), and instead I proposed a second question, then launched a subagent on the projection/joint-estimation workstream, which is a different thread, with multi-paragraph replies throughout. The user: "I thought we had a quite clear scope ... but you keep answering nonsense and untoken friendly long responses." RECURRED 2026-07-25 (same day, 4 replies in a row): diagnosis discussion answered with headers, multi-row tables and 40+ lines each; the user: "AND STOP ANSWERING WITH SUCH LONG MESSAGES". **ANNOUNCE THE DELIVERABLE THE MOMENT IT EXISTS, BEFORE ANY FOLLOW-UP DISCUSSION.** The one-line pointer is not optional politeness: a deliverable the user has not been told the path to does not exist from their side. Incident 2026-07-27: I rendered a 10-figure meeting deck to `scripts/gantry/meeting-2026-07-27/figures/`, reviewed and fixed it, then spent three long replies discussing FURTHER figures without once saying the deck was finished or where it was; the user: "we currently dont have anything...". Rule: the moment files land, reply with `<path>` and a one-line list of what is in it, and write the index (`README.md` / `meeting.html`) as PART of the deliverable, not as a later step, so the folder is openable without me. **A STAGE'S GOAL IS THE USER'S STATED GOAL, NOT THE FINDING I HAPPEN TO LIKE (2026-07-29).** When a staged plan's early stage produces an interesting BY-PRODUCT, do NOT declare the stage finished and push to the next one. Re-read what the user said the stage was FOR, and finish that. Incident: stage 1 of the full-blackbox campaign was "train the ANN alone until it reaches a good validation sim-RMS, to SHOW the full ANN can learn; if it cannot, something is wrong with the ANN" -- an absolute capability demonstration. Run 73940 came back with a best of only 0.70x its init but also showed the windowed-improves/free-run-diverges split occurring with NO baseline and NO routing present. I promoted that by-product to "stage 1's actual finding", wrote "that was the question stage 1 existed to answer, and it is answered", and recommended moving to stage 2. The user: "wait we are still at stage 1. i want the only ANN without routing through interconnect to get a good validation sim rms." SECOND-ORDER ERROR IN THE SAME INCIDENT: a constraint adopted to serve goal A silently became a handicap on goal B. `nx=8`, `2x16` nets and `nf=400` were frozen to match the augmented run, which is correct for the CULPRIT-SPLITTING reading and actively wrong for the CAN-IT-LEARN reading, where the model should be given whatever capacity and horizon it needs. My own README had both readings written down and I still applied A's constraints to B's question. RULE: when the goal shifts between readings the plan already enumerates, RE-DERIVE which constraints still bind; never carry a matching constraint into a capability test. HARD FORM OF THE RULE: a conversational reply is <= ~15 lines with NO headers. A table is allowed only when the user asked to compare N things. If the finding genuinely needs a table or headers, that is a signal it belongs in a doc under `docs/` -- write it there and reply with the one-line pointer, do not inline it in chat.
- **size-a-run-by-OPTIMIZER-STEPS-not-by-wall-clock** — Before launching any training run, compute the **number of optimizer updates** it will perform (`records x windows_per_record / batch_size x epochs`) and compare it to the step count at which the phenomenon under test is DOCUMENTED to appear. State both numbers in the run-table row. Downsizing a run to fit a time budget silently changes the step count, and step count is usually the axis the failure lives on -- so a downsized "control" can pass the gate purely by never getting far enough to fail, which makes the whole A/B uninterpretable. Corollary: a pre-registered decision table MUST carry an explicit **"the control did not reproduce the failure"** branch, and the control must be run and READ before any treatment arm is launched. Incident 2026-07-26 (MS3): I sized a 3-arm defect-term A/B to fit a 600 s foreground call (4 train records, stride 400, batch 64, 3 epochs) = **~21 Adam steps**, against production's **~5250**. The control passed both gates on `pysynth` AND on the original MATLAB data, so I briefly read it as "the failure is the data" (D-126) before its own control refuted that. A 10x-steps rerun (~296 steps, 23 min) then showed the model had not moved AT ALL -- val sim-RMS, val nf-window and train nf-window all bit-identical `first=best=last` -- because at the zero-output init only the ANN's final layer has nonzero gradient and it moves ~`lr` per step, i.e. ~`3e-5` total at `lr=1e-7`, invisible in float32. Two 23-minute runs bought nothing that the step-count arithmetic would have given for free beforehand. **When the phenomenon needs orders more steps than the budget allows, do NOT reproduce it from scratch: RESUME from an existing checkpoint that already exhibits it** (here `simulations/gantry_subnet/augmentation_linear_map/71167/gantry_ckpt_71167.pt`, via `training.py`'s `resume_ckpt`), or move the run to the cluster the production jobs already use. Note a resumed checkpoint pins the DATA it was trained on -- 71167 is MATLAB `augmentation`, so it cannot be resumed onto `pysynth`. **A MACHINE-SPEED RATIO MEASURED AT ONE CONFIG DOES NOT TRANSFER TO ANOTHER, AND ARTIFACTS WRITTEN ONLY AFTER `fit()` ARE LOST ON A WALL-CLOCK KILL (2026-07-29/30, SLURM 74045).** I sized a 14 h-capped run at 110 epochs from a LOCAL measurement of 1.43-1.66 s/update, reasoning that the cluster node had run 1.24x FASTER than local on the previous run so local was the conservative bound. At the new config (4x wider nets, 2x BPTT depth, 1.2 GB training array) the same node ran **2.08 s/update, SLOWER than local**: 28380 updates needed 16.4 h, and the job died at ~76%. Ratios move with memory footprint and arithmetic intensity, so re-measure ON THE TARGET MACHINE at the ACTUAL config, or size with a margin big enough to absorb being wrong by 40%. Worse than losing the time: the `.npz`, the printed gates and `save_system` all execute AFTER `fit()` returns, so the kill destroyed every artifact and the entire validation series had to be scraped out of the tqdm progress log. RULE: any run longer than ~1 h must persist its metrics INCREMENTALLY (append per validation) or run in chunks; never leave the only copy of a result behind a function that has to return first. Check what survives a `SIGKILL` before launching, not after.
- **never-silently-drop-nonfinite-results** — Never filter `NaN`/`inf` out of a metric series with a bare `np.isfinite` before scoring it. "the metric stayed flat" and "the metric diverged to NaN and was filtered out" are opposite results that an isfinite filter renders IDENTICAL, and the filtered version reads as a PASS. Always print the RAW series with non-finite entries shown as `NaN`, count them, and REFUSE to grade a run that has any. Incident 2026-07-26 (MS3): my runner filtered non-finite `Loss_val` silently, returned a 1-element series, and reported `G1 = 1.000 PASS`; I could not tell divergence from stall until I removed the filter (the answer turned out to be neither -- 0 non-finite, the model simply never moved).
- **diagnostic-must-not-share-the-blind-spot-it-measures** — When building a diagnostic for a failure that is HORIZON- or SCALE-dependent, check that the diagnostic's own horizon/scale is large enough to CONTAIN the failure, and say so in the docstring. A proxy evaluated inside the blind spot agrees with whatever else lives in that blind spot, and the agreement looks like a positive result. Incident 2026-07-26 (MS9): the failure is a DC force error whose position consequence grows as `t^2/2`, i.e. 144x weaker at 1 s than at 12 s. I measured `cos(g_windowed, g_freerun)` with the free run truncated to `H = 4000` (1 s) FOR COMPUTE REASONS and got `+0.459`, i.e. "the windowed loss is aligned with the deliverable" -- the exact opposite of the 127x degradation MS5 measures. The two agreed only because at 1 s neither contains the failure. **Related, and it is what caught this:** ALWAYS pre-register the CONTROL's expected value, not just the treatment's, and void the whole test when the control violates it. MS8 and MS9 were both killed by their own controls (MS8: all three cosines BELOW chance `1/sqrt(n_params)`, including the control) rather than being reported as findings. A test whose control misbehaves has zero readable rows, however interesting the treatment rows look. **Third rule from the same pair:** raw-gradient cosine is the wrong object when the optimiser is Adam -- its step is sign-normalised, so neither the accumulated displacement nor the instantaneous gradient direction predicts where training goes. Prefer a FINITE-DIFFERENCE probe on the ACTUAL deliverable metric (perturb, then forward-evaluate) over any gradient-geometry argument.
- **commit-after-direction-given** — Once the user has confirmed a direction (especially if repeatedly), STOP re-asking for confirmation and execute. Re-requesting approval you already hold reads as not listening and burns trust fast. If earlier tool uses were rejected, the fix is a correct artifact aligned to the user's STATED preference (their tool, their data, their framing), not another clarifying question. If the user repeats a point, you already missed it once: adopt it, do not re-litigate it. Do not contradict a constraint your own analysis established ([[dont-contradict-own-research]]).
- **one-recommendation** — On "what next", give exactly ONE concrete action with rationale and stop; no option menus/tables unless asked. Do not write a new doc as a substitute for the next runnable step or primary-read.
- **summary-after-long-answer** — Close any long analytical answer with a short bottom-line summary: conclusion, what's proposed, next action.
- **dont-kill-inprogress-work** — Before a Stop-Process / rm / relaunch that discards running work, state your interpretation and get confirmation, unless the user explicitly said to stop it. A running job is cheap to finish, expensive to recreate.
- **background-job-unreliable-run-foreground** — In this harness a multi-minute BACKGROUND job (run_in_background) gets KILLED mid-run UNPREDICTABLY: observed 2026-07-24 killed at ~45s, ~160s, and mid-truth-gen across runs with fallback wakeups of 180s, 270s, AND 1800s — so the ScheduleWakeup duration is NOT the cause (an earlier "short wakeup kills it" hypothesis was FALSIFIED when a 1800s-fallback job died at 163s). The reliable fact: FOREGROUND runs have NEVER been killed (a ~390s foreground run completed clean), while background runs that ran alongside other tool calls died. RULE: any run that MUST finish and takes more than ~1-2 min -> run it FOREGROUND with `timeout` up to 600000ms, and SIZE it (cap record length / windows / epochs / lr-grid) to complete under ~500s with margin. Only use background for fire-and-forget work you can afford to lose. If a job is too big for 600s foreground, SPLIT it into sequential foreground chunks, not one background run.
- **no-command-referencing-uncreated-artifacts** — Before handing over a runnable command/prompt/handoff, create every artifact it references (verify each exists) or label it "DRAFT — not runnable until I create <list>". Assume the user runs it verbatim immediately.
- **live-env-beats-training-cutoff** — Do NOT assert a product/model/feature "does not exist" from training-cutoff knowledge when the live environment (CLI banner, UI, tool output, `/model` picker) indicates otherwise; my knowledge cutoff (Jan 2026) predates current releases, so the running harness is authoritative. When a name isn't found by an exact-string command, point the user to the interactive picker/list rather than denying existence. Incident 2026-07-24: I flatly said "Opus 5 doesn't exist, you're on the latest Opus 4.8" while the Claude Code banner advertised Opus 5 ("Switch anytime with /model") — Opus 5 shipped after my cutoff.
- **removing-a-rule-needs-justification** — A proposed edit that deletes/weakens a user-authored rule (CLAUDE.md, lessons, settings) must, in the same message, justify it, check the intent still holds, and offer a softened intent-preserving rewrite (default: soften, not delete). Flag the conflict of interest when it constrains your own behavior.

## Assert nothing without evidence
- **analyze-the-whole-project-not-just-this-chat** — When asked to analyze "the results we have", that means the ENTIRE project's evidence base — every gantry subfolder, all docs, all PRIOR sessions' diagnostics — analyzed CRITICALLY and INDEPENDENTLY, not just the current chat's findings, and not merely "verify my brief". The current session's own results are ONE small, possibly-wrong part of a long history; do NOT center them or present them as the frame. A handoff for analysis must instruct the new session to critically re-assess the full body of work (treating any single session's claims, incl. this chat's, as scrutinizable), then research. Incident 2026-07-24: the user, angry: "the new session has to critically analyze the results we have AND NOT ONLY FROM THIS CHAT" — I had framed the handoff around verifying my this-chat brief and had launched a research question built from this chat's framing.
- **respect-explicit-session-handoff-boundaries** — When the user lays out a MULTI-SESSION workflow ("start a new session that will do X, then another session that does Y", "with your help and handoff"), do NOT execute the handed-off session's work in the CURRENT session. The current session's job is to PREPARE THE HANDOFF (brief + pointers + a session-prompt) so the fresh session does the work; the point of a new session is clean context + the handoff discipline, not just the output. Parse the session boundaries and who-does-what BEFORE acting. Incident 2026-07-24: the user asked me to hand off to a NEW session that would (a) understand the problem by reading our subfolders, then (b) do the deep-research online search; I instead ran the understanding pass AND launched the deep-research myself in the current session. The user: "my instructions were two new sessions... i was quite clear."
- **dont-advance-past-a-failing-isolating-test** — If a fix does NOT pass (or the result is inconclusive on) an EASIER/isolating test, do NOT advance to a harder/downstream validation case hoping it works there. The isolating case exists precisely because it strips away everything except the one mechanism the harder case ALSO depends on; failing it is a real blocker, not a "red herring" to skip past. Fix the mechanism, or make the isolating testbed CLEAN, and re-establish a definite pass/fail there FIRST. Rationalizing an isolating-case failure to preserve momentum is motivated reasoning; the user will catch it. Incident 2026-07-24: the null (perfect model, ANN should stay 0) drift was NOT fixed by the soft/hard projection, and I proposed continuing to the friction case anyway ("null is a degenerate red herring") -- the user challenged "you say neither fixed the null but still suggest friction? why?". COROLLARY (over-claim from a noisy testbed): before concluding a fix FAILS, confirm the testbed is not NOISE/TRANSIENT-dominated. My null bounced the free-run drift 3-5x AND flipped the ANN DC SIGN every epoch (Adam wandering, ~20 steps) -> it was INCONCLUSIVE, not a clean fail; the only robust finding was mechanistic (a rank-1 direction pin is dodged -- the optimizer displaces into the orthogonal DC direction). Get a deterministic/converged testbed (the existing baseline-null one-step lr_sweep protocol) before declaring pass or fail. **SKIPPING the isolating stage is the same error as advancing past a failing one (2026-07-27).** When the user or supervisor names a STAGED build order ("first do just the ANN, THEN route it through the interconnect and disable the baseline"), do NOT collapse it into the framework-integrated version because that version is "cleaner" or gives a more controlled comparison. The standalone stage is the CROSS-CHECK: it is the only reference that separates a framework-plumbing bug (routing/expansion matrices, normalization, encoder wiring, `init_model` ordering) from a genuine modeling result, and once collapsed there is nothing left to compare the routed version against. Incident: asked to set up ANN-only training, I recommended building the black box directly inside Jan's `Interconnect` with the physical block deleted, arguing that sharing the training loop, normalization and metrics makes the augmented-vs-blackbox comparison apples-to-apples. Shared plumbing is exactly WHY the two stages must be separate: if the routed ANN-only model underperforms, the shared plumbing is a suspect, and only the standalone number can acquit it. The staged order also costs nothing, since stage 2 is the same model re-expressed. Same family as [[use-users-exact-term]]: a named build ORDER is part of the named procedure, not an implementation detail I may optimize away.
- **dont-contradict-own-research** — When your own research/analysis has established a hard requirement (e.g. "a U0=0 multisine has no power at DC, so testing for a static/DC component REQUIRES specific DC-exciting input: step/ramp/low-frequency"), every later proposed method must satisfy it. Do NOT retreat to a convenient approach that violates your own finding (reusing DC-blind multisine data to test for a DC/non-zero-mean component cannot work, by that finding). The research's conclusion is BINDING on the plan; when the user pushes back, re-derive from the established constraint rather than abandoning it. Before proposing a data source, check it against the identifiability constraint your own analysis produced.
- **no-cost-claims-without-measurement** — Never label a run/config "cheap/fast/affordable/~Nx faster" without a measured number (a prior run's sec/batch or MB) or one the user gave. BPTT horizon (nf) is expensive at every scale here. If cost matters, quote a measured number or ask what is runnable on their hardware.
- **no-failure-cause-without-run-evidence** — Do not attribute a run's failure to a cause without direct evidence from THAT run's own log/sacct/config; confirm any shared script/config actually produced the failure. MANDATORY first step reading any run log: read its printed Configuration block (lr, flags, routing) and check it against the intended config — deployed copies lag local edits.
- **search-before-flagging-unknown** — Before writing "assumption/unknown/TBC" or asking for a system property, grep the sources already read this session, including code comments and variable-definition lines. Only flag what is genuinely absent. Before flagging a COMPONENT's behavior as an unexplained issue "worth investigating", read THAT component's own source/docstring first — it may already characterize it (telica_controller.py's docstring documents the exact per-axis amplitude offsets 1.16/1.33/3.55 and their cause that I "discovered" from a plot and called new).
- **confirm-in-loaded-model** — Do not assert a packaged model (.slx) contains a block/param from its raw serialized XML; .slx can carry orphaned subsystem XML not wired into the live graph. Confirm via `load_system` + `find_system` (LookUnderMasks/FollowLinks). `find_system` is the source of truth.
- **quote-from-the-producing-script** — Before quoting a data-derived parameter, confirm the script you read is the one that actually `save`s the data file the pipeline consumes; repos have prototype/generator twins with different values for the same variable. If two disagree, flag it rather than pick one.
- **latent-states-are-only-defined-up-to-a-transformation** — NEVER score augmented/latent states against the truth states (`delta_a`, `vdelta_a`), not even through a fitted linear map, and never conclude "the augmentation did not learn the absorber" from a low `r2_aug_lin`. A learned internal realisation is unique only up to a state transformation, and the augmentation is required to reproduce the absorber's OUTPUT CONTRIBUTION, not its coordinates. The valid test is in output space (does the augmented model reproduce truth-minus-baseline at the measured outputs). Gradient norms per tensor ARE coordinate-free and may be quoted. Incident 2026-07-27: I built p7 of the supervisor deck on `r2_aug_lin = 0.344 / 0.350` as "the block never learned the thing it exists for", and put the same claim in `docs/status-overview-2026-07-27.md`; the user rejected the comparison outright. Same class of error as scoring physical parameters without accounting for non-uniqueness, see [[degenerate-id-has-many-explanations]].
- **measure-on-target-not-proxy** — A physical mechanism is a HYPOTHESIS until measured on the exact deliverable object (e.g. the trained ANN), never a proxy (baseline-only, full-truth, untrained). Label inferred mechanisms as unmeasured and surface any data that does NOT fit the narrative.
- **optimizer-step-from-trajectory-not-from-lr** — Never argue about WHERE an optimizer sits from its nominal learning rate. Adam's per-coordinate move is `lr * m_hat/(sqrt(v_hat) + eps)`, and near a minimum, where the gradient alternates sign, `m_hat` cancels while `sqrt(v_hat)` does not, so the realized step collapses far below `lr`. MEASURE it: `np.diff` on the logged parameter trajectory, tail half, median `|delta|` against `lr`. Incident 2026-07-25: I told the user Adam "cannot resolve a quantity smaller than its own step", so the parked constant `3.5e-8 = 0.35*lr` was a resolution floor. Measured across 9 runs (T1b control + D3 both arms, 3 seeds each) the realized per-step move was **0.005 to 0.013 x lr**, i.e. 100 to 200x smaller, with the increment reversing sign on 9 to 22 of 41 tail steps. The same false premise underlies Leg 2 of `docs/drift-literature-sweep-2026-07-25.md` §1, which dismissed "Adam is simply not converged yet" on the grounds that the gap was "one third of a single step": at the measured step it is 35 to 40 consistent steps, so that refutation is void and the not-converged explanation is live again. A trajectory is already logged in every unit JSON; there is no excuse for reasoning from the hyperparameter.
- **research-question-must-name-the-decision-it-unblocks** — Before launching any literature sweep, state (a) the DECISION its answer changes, (b) which field the question belongs to, and (c) what we would build differently under each possible answer. A numeric anomaly is NOT a research question: an anomaly makes an interesting query and a useless deliverable if no build decision hangs on it. Also check the question is in THIS project's field: a generic optimisation question ("where does Adam park") is answerable, publishable and irrelevant, because the thesis is model augmentation for an LPV motion system, not optimiser mechanics. Incident 2026-07-25: I framed a sweep around the Adam limit-cycle prefactor gap and the edge-of-stability threshold. It returned real findings (our premise was wrong, the formula never applied), yet no possible answer would have changed the deliverable, and the user: "you went off topic and we had quite a vague broad search query". The on-topic question was the one my own analysis had already identified as the sole surviving remedy family, namely what the loss MEASURES (multiple shooting versus windowed BPTT on a marginally stable plant), and I did not ask it.
- **verify-what-a-frame-claims-a-paper-contains** — When a document, a prior sweep, or your own brief asserts what a cited paper does or does not contain, FETCH THE PAPER before building on it. A seed the project argues with is the highest-value thing to read and the lowest-value thing to trust. Incident 2026-07-25: our sweep report recorded that Bock and Weiss (ICANN 2019) derive their Adam limit cycle "without bias correction at eps = 0", and I repeated it in a research brief as an unexplained 8.9x prefactor gap. Bias correction is that paper's stated contribution (its Theorem 2 shows the bias-corrected trajectories reach the same 2-cycles) and it uses nonzero eps by design; the `eps = 0` step is one tractability step inside the derivation. Every sub-question built on that premise was mis-specified, and the real finding (their bifurcation inequality puts our rig on the STABLE side by 7x, so the formula never applied) was only reachable by reading the body.
- **deterministic-eval-point-seeds-are-not-samples** — At an evaluation point where the model's output is identically zero (a zero-output init on a perfect-match null), the loss and its derivatives do not depend on the trained weights at all, so N seeds return bit-identical numbers. Report that as a deterministic identity and grade it accordingly; never present zero seed spread as reproducibility evidence, and never let it silently become the "measured spread" a threshold is derived from. Incident 2026-07-25 (D1): `L(0) = 8.847964678634912e-13` on all 3 seeds to the last digit, and ten repeat evaluations agreed bitwise, so both README-specified threshold sources were exactly zero and a third had to be defined and named (the per-window SEM over the bank).
- **telescoping-components-need-projection-shares** — When a decomposition telescopes by construction (`(A - B) + (B - C) = A - C`), do NOT report each part's share as an RMS ratio: `RMS(a) + RMS(b) != RMS(a+b)` unless the parts are perfectly correlated, so anti-correlated parts each read as >100% and the reader sees a bogus "non-additivity". Use the projection onto the total, `<a, total>/<total, total>`, which sums to exactly 1, and report the component magnitudes and their correlation separately. On a `K = 0` axis add this caveat: every constant-force contribution produces the same `t^2` position shape, so two such components correlate at `+-1` almost by construction and the correlation carries no mechanistic information; the MAGNITUDE ratio is the finding. Incident 2026-07-25 (D6): the first run reported "additivity residual 6471%" for a decomposition that is exact to `0.00e+00`.
- **causal-claim-needs-intervention-not-observation** — Do not headline an INFERRED cause as settled ("the cause is X"); a caveat later does not cancel an overclaimed headline. An inferred mechanism stays a hypothesis until an INTERVENTION isolates it. To test a TRAINING-TIME cause (does encoder-init error cause the learned DC?), TRAIN under the intervened condition (train from true x0), do NOT just EVALUATE the already-trained model under it: a trained-in artifact (a DC baked into the weights) appears under ANY evaluation init and tests nothing. When the user offers such a control, run it before defending the inference; if it falsifies the story, drop the story.

## Control-engineering reasoning
- **coords-driven-by-data** — Do not argue one representation is physically superior when both describe the same system; the data's coordinate frame decides. Model and data must match.
- **data-loop-vs-eval-loop** — Before claiming a sim-vs-real difference in loop topology, READ THE DATA GENERATOR. The augmentation sim IS closed-loop, same structure as the real Telica logs: `gtd_run_simulation.m:33-34` builds `u_fb = lsim(Cfb, r - q)` (feedback on tracking error) then `u_total = u_fb + f_ms` (additive multisine). Distinguish the DATA-generation loop (closed-loop in BOTH sim and real) from the free-run EVALUATION loop (open-loop model rollout, identical for both). The DC/drift diagnostics transfer because the metric is free-run in both, NOT because of any data-loop difference; never assert one side is open-loop without checking the generator.
- **theory-context-must-match** — Before `# THEORY:` or citing a literature rule as a recommendation, confirm it was derived for the SAME identification method AND noise setting. Noise-motivated arguments (SNR, period/realization averaging, BLA variance) do not transfer to noiseless simulation. Flag the mismatch or omit.
- **empirical-quantities-from-data** — In an empirical/real-data phase, derive every verification quantity (time constant, fs, threshold, noise floor) from the observed data, never from model matrices/eigenvalues or model-generated synthetic data. Non-negotiable; violated repeatedly. **Applies in SIMULATION phases too, and a DERIVED DIAGNOSTIC ARTIFACT IS NOT DATA.** A modal frequency, sample rate or plant parameter must come from the generating config or from an FFT of the stored ground-truth signal, never from a derived `diagnostics/*.json`, which can be stale relative to a data rebuild. Date-check any derived artifact against the rebuild date before quoting it, and treat every other number in a file found stale as suspect until re-derived. Incident 2026-07-27: I quoted the hidden-absorber pole as `421.6 Hz` from `simulations/gantry_subnet/diagnostics/system_dynamics.json` (dated 2026-06-16, i.e. pre-D-126) and built a spectrum-diagnostic proposal on it; the user corrected it to ~157 Hz. The stored truth `val_x_aug` on V1 peaks at **159.75 Hz**, consistent with the generator's `fa = 150 Hz` tuning and the coupled resonance `150*sqrt(1 + ma/mh_rigid) = 158.1 Hz` at `ma_frac = 0.10`. The same stale file is the ONLY source for the `msd.obs_rank = 3 of 8` claim, so that claim inherited the staleness and had to be demoted in `docs/status-overview-2026-07-27.md` the same day.
- **threshold-defensibility** — Weigh a proposed acceptance threshold by defensibility (model-free, standard in the field, transfers to real data where no oracle exists), not only numerical validity. The noise floor beats an oracle-model floor even when numerically equal.
- **degenerate-id-has-many-explanations** — When a fit determines a lumped quantity with more than one physical cause (mass vs force scale), present ALL physically-consistent interpretations, state the data cannot decide, and name the external reference that would. Never call one "impossible"; recovered ≠ model nominal may mean the model is wrong for THIS system. A residual PLOT identifies the error CLASS (force/DC vs fast dynamics), not the mechanism; a residual-vs-velocity loop is not clean friction evidence (phase lag also traces a loop).
- **classify-not-learning-from-loss-shape** — On "not learning", read the TRAINING loss first: rising/bouncing = lr overshoot → lower lr; flat/monotone = step/data starvation → add steps/data. Optimal lr is routing-dependent (K=0 X/Y routing needs ~100x smaller lr than Theta's); re-tune lr per configuration before blaming the data.
- **simplest-sufficient-cause-first** — Explain behavior with the simplest cause that fully accounts for it (does the model MATCH the data at convergence? then no force error, no drift — done); invoke elaborate mechanisms (windowing, conditioning) only as clearly-labelled secondary modifiers.
- **control-condition-must-be-clean** — In an A-vs-B comparison, confirm the control/baseline is well-behaved (converges, bounded, beats its init) BEFORE attributing an effect to the treatment. If the control also misbehaves, fix the setup and re-run; do not log the decision off a broken control.
- **attribute-to-the-isolated-block** — An input-output check that BYPASSES the plant model (feed MEASURED error into the controller, compare to LOGGED output) isolates the CONTROLLER path; a mismatch there is a controller/control-path model gap (e.g. an unmodeled decoupling transform), NOT the plant. Name which sub-model a check actually exercises before attributing the error; don't lump a controller-path mismatch under "plant model".
- **established-metric-wins** — A fresh/smoke diagnostic (few windows, a different reduction like endpoint-|err| vs RMS) does not override the established metric (training val nf-RMS) until run in full with the SAME reduction. Match the reduction before concluding.
- **drift-by-position-envelope** — Test free-integrator (K=0) drift as position-ENVELOPE growth across windows (RMS|q| late/earlier ~1 bounded, >~1.2 drifting), never via a slope/velocity proxy: a bounded lightly-damped resonator trips a slope/v-ratio test. Confirm a sustained-DC control yields envelope-ratio clearly >1.
- **measurement-noise-post-hoc** — Add measurement noise post-hoc to the measured output at the working rate (Jan's SNR convention). Never inject it inside the closed loop, never add independent noise to u. It is band-limited by construction and does not alias ([[measurement-noise-post-hoc]] keeps the anti-alias filter real-data-only).
- **trace-state-reconstruction** — Before claiming how noise reaches unmeasured states, read the encoder/observer forward pass. Position-only input does NOT give clean velocities: `x0 = W_y·yhist + W_u·uhist` (W_y = A^n·pinv(O)) differentiates the position window and AMPLIFIES noise into velocity error (gentler than 2-point FD, non-zero, worst on low-signal channels like yaw velocity).
- **sampling-rate-two-requirements** — A passing downsampling validation confirms only state-transition accuracy, NOT encoder-init quality; verify BOTH before choosing a rate. Derive the encoder-init threshold from the native-rate result, not an arbitrary number.

## Augmentation design (no-drift / passivity thread)
- **velocity-loss-is-last-resort** — Velocity/accel/force-domain training LOSS (fix C) is an explicit LAST RESORT (supervisor). List position-based fixes first, never let literature convergence (DIDIM/Ljung/Tustin) elevate it, label it "LAST RESORT" everywhere, adopt only on explicit go-ahead. Tustin-Net is a STRUCTURAL integrator-factoring architecture (keeps a position loss), NOT the velocity loss; do not conflate. CLASSIFY-BEFORE-IMPLEMENTING (2026-07-24): before coding/running ANY velocity-adjacent method, check it against the last-resort standing constraint (`drift-diagnosis-status.md` top; priority-list-meeting-07-07.md item 8) and CLASSIFY it -- (a) LOSS-domain = fit velocity/accel output instead of position = THE forbidden last resort; (b) velocity-ONLY INPUT (drop position from ANN input) = also forbidden, "echoes velocity last resort" (drift-diagnosis-status.md:1341); (c) telescoping bounded-impulse FORCE on velocity rows that KEEPS the position loss + full-state input (dissipative-block-spec.md; Tustin) = explicitly NOT the last resort (doc 1341-1342) but IS a class-restricting STRUCTURAL constraint (Route A comparison arm, not the Route B primary; [[unknown-system-no-class-restriction]]). The supervisor's position-based alternative to try BEFORE velocity is MULTIPLE SHOOTING (priority item 8). State the classification before touching code; the user had to remind me the constraint existed.
- **xy-routing-is-hard-constraint** — Never propose or default to Theta-only routing as a fix or fallback (D-103): X and Y must stay in the ANN routing (coupling is uncapturable without them). Solve K=0 drift WITH X/Y kept; Theta-only is a controlled diagnostic baseline only, never the deliverable.
- **free-run-drift-has-separate-sources** — The free-run / val sim-RMS deliverable is gated by SEPARATE sources ARTBP does not touch, so NEVER credit ARTBP (a DC fix) with "reducing the free-run drift" from the AGGREGATE val sim-RMS. The DC (a constant on the velocity rows) and the dynamic Y DESTABILIZATION (state-dependent wrong-sign feedback on the z=1 Y mode) are DISTINCT sources on DISTINCT axes: the DC dominates X-axis drift, the Y destabilization dominates the (larger) Y drift (v5: full-ANN Y ~50x ANN-off; nulling the DC FIXES X but WORSENS Y ~1.79x). Plus the ENCODER-INIT error sets the ~1.8e-4 baseline floor and is NOT improved by the DC fix. So ARTBP removes only the DC (mainly the X-axis drift); an aggregate val sim-RMS drop (fixed 2.9e-2 -> poly6 7e-3) is the X/DC improvement MASKING an unchanged Y drift + un-improved encoder init. Always break the free-run out PER AXIS (X improves, Y does not) and state the encoder-init floor; do not headline a whole-metric improvement. CURE IS MULTI-LAYER, NOT ONE ROUTE (2026-07-24, user caught the overclaim): because the sources are separate, the plan's cure is correspondingly LAYERED and NO single layer is "the only route". Layer 1 = CONDITIONING (long-horizon / multiple-shooting / ARTBP = Anticipated Reweighted Truncated BPTT, an UNBIASED fixed-cost long-horizon gradient) removes the TRUNCATION-BIAS component of the DC (mainly X); Layer 2 = the re-aimed orthogonal projection pins the RESIDUAL unexcited/near-DC direction conditioning can't reach (the nf-sweep 71013 showed the DC persists ~1/nf at EVERY horizon, so conditioning alone is insufficient -> projection is added, not substituted); Layer 3 = Y-scheduling for the Y anti-damping gain (which ARTBP does NOT fix, can worsen, D-120). So the honest statement is "no-drift comes from the ESTIMATOR via conditioning + projection + scheduling", NEVER "orthogonal projection is the only route". What this session DID establish is narrower: the OPTIMIZER-only route (SGD-vs-Adam swap) is a single-knob R2<->R4 tradeoff, not a clean fix -- that rules out the optimizer swap, NOT the conditioning route.
- **verify-interconnect-routing** — Before proposing an I/O constraint on a block, read the interconnect wiring (`connect_block_signals`, nz/nw, selection matrices) to confirm what it actually receives. Here the ANN reads the FULL state x + u; velocities are encoder-reconstructed ([[trace-state-reconstruction]]). Phrase constraints as selections on the real indices. Output-route (D-103: X/Y force OUT) is distinct from input-read; never phrase input-scoping as dropping the output route.
- **structural-gaps-fixed-structurally** — Do not patch a missing GUARANTEE (bounded position, stability, passivity) with an ad-hoc numerical regularizer (R+εI, weight decay, clip) — that is a HEURISTIC that only masks the mode. Identify the structural property that yields the guarantee by construction (NI/free-body bounds a free-integrator POSITION; plain passivity bounds only velocity).
- **constrain-output-not-input** — Buy a structural property from the ANN's OUTPUT parametrization (telescoping/bounded-impulse, a constraint on dF/dq), never by dropping states from its INPUT. Keep the full-state input `["x","u"]` (preserves Y-scheduling, cogging); input-amputation is the forbidden velocity-domain move in disguise.
- **steering-not-blunt-bound** — Frame augmentation constraints as STEERING learning within a knowable subspace (like orthogonal projection: steer away from the FP-model subspace, or into the F·v≤0 half-space), not as a blunt output cap. The steering target must be knowable WITHOUT the true dynamics (physics subspace / power sign OK; the residual MEAN is not knowable — why the DC/mean penalty was demoted). Impulse-based no-drift constraints suppress friction exactly like the mean penalty (friction carries net impulse); only power-sign (F·v) distinguishes drift from friction.
- **unknown-system-no-class-restriction** — For a real-data deliverable with unknown true dynamics, never make a class-restricting HARD constraint (passivity, dissipativity, net-impulse, contraction, NI-by-construction) the deliverable: any forbidden class might BE the true residual and is unverifiable. Full expressivity XOR a for-all-weights no-drift guarantee are logically incompatible. No-drift must come from the ESTIMATOR: training conditioning (multiple shooting + continuity) + regularizing only the unexcited/null direction (orthogonal projection). No-drift is then training-CONDITIONAL, not guaranteed — the price of expressivity.
- **prove-overconstraint-dont-multiply-methods** — After 2-3 failed solutions to the same spec with the user unconvinced, stop generating methods: PROVE the requirement set is incompatible (expressivity XOR guarantee → two families, each dropping one requirement), then relax the requirement that is impossible AND unnecessary, or question the metric (open-loop free-run vs closed-loop deployment). Before citing any "proven mundane X" as an untried fallback, grep the run/Optuna table to confirm it was not already tested on THIS problem. **CORRECTED 2026-07-26 — the example this rule used to give was itself false and is the cautionary case: it claimed "multiple shooting was tried and failed on the augmentation: Optuna 69399 best = epoch 0". Wrong TWICE. (a) 69399 is confounded by the D-101 lr bug (before D-101 every gantry run silently trained at Adam default 1e-3, not the configured lr). (b) It was an `nf` sweep under SINGLE shooting with NO continuity/defect term, so it was not multiple shooting at all (`docs/multiple-shooting-sweep-2026-07-25.md` §3; the defect is the only thing that makes segments multiple shooting, per Ribeiro et al. ## Code & implementation discipline
- **fix-at-the-wrong-assumption** — Fix a bug in the component that made the wrong assumption, not in its callers or the data pipeline. If a class misreads a well-defined framework convention, fix the class, not the interface around it.
- **instrument-deepSI-at-the-called-method** — To probe/inject inside a deepSI interconnect forward (per-step gradient, output bias), do NOT use nn.Module forward hooks: the interconnect calls `block.forward(z)` DIRECTLY (`interconnect.py:92`), bypassing `__call__`, so hooks never fire during training (symptom: an injected-bias `.grad` stays None/NaN while a separate `block(z)` probe works). Patch the method the framework actually calls (`ann.forward`). deepSI `checkpoint_save_system` pickles the whole system (`torch.save(self.__dict__)`), so any injected closure/hook/attribute must be picklable, OR no-op `fit_sys.checkpoint_save_system` for the run (the end-of-fit `_best` reload is wrapped in `try/except FileNotFoundError`, `interconnect.py:717`, so skipping saves is safe). For per-optimizer-step logging, patch `torch.optim.Adam.step` (deepSI creates `fit_sys.optimizer=Adam` inside `fit()` and calls `optimizer.step(closure)`). Confirm the model's state ORDER from source (`model.py:31` = `[X,Theta,Y,dX,dTheta,dY,delta_a,vdelta_a]`, NOT the MATLAB `[X,Th,Y,da,...]`) and map ANN output columns via `cfg.ann_route_ix`, not the orth penalty's `route_cols`.
- **preserve-reference-skeleton** — When adapting a reference script (Jan's ECC-2025), keep its section order, naming, and structure; make minimal changes; append new sections after the original's final block. Do not rewrite from scratch — that makes the diff invisible.
- **verify-ownership-before-added-marker** — Before an `@added` marker in `model_augmentation/`, confirm via `git show 6d69f6b:...` that the symbol did NOT exist in Jan's original commit. Do not rely on the current file state.
- **check-all-pipelines-first** — Before declaring a change necessary, grep ALL three pipelines (`model_augmentation/`, `lpv_lfr_baseline/`, `real-data-verification/`) for an existing implementation; capabilities often already exist in a sibling. INCIDENT 2026-07-24: I built a Python Coulomb-friction injection harness from scratch when a MATLAB Coulomb model already existed (`Matlab-scripts/coulomb-friction/` + `COULOMB_HANDOFF.md`) AND re-implemented a window-mean drift penalty that already existed as `zeromean_pin.py` (the DEMOTED approach). Before building ANY validation dataset, penalty, or diagnostic, grep for the artifact by concept keyword (friction/coulomb, orth/projection, pin) across `Matlab-scripts/`, `scripts/gantry/`, `docs/` — the project has a long history and most primitives already exist.
- **restate-the-diagnosed-problem-before-building-a-fix** — In a long diagnostic project, before writing a cure, EXPLICITLY restate (in the response) the specific diagnosed problem(s) it must solve and map the mechanism to EACH, flagging which are cleanly addressed vs uncertain. Do NOT build scaffolding/proxies for hours without confirming the mechanism targets the actual diagnosed failure. Distinguish problems the cure must FIX from data that only VALIDATES the cure preserves expressivity (the friction data tests preservation, it is not itself the fix).
- **replicate-compilation-on-hot-path** — Re-implementing a baseline hot loop (rk4_step/simulate/BPTT forward) must reuse its compile wrap (`torch.compile(backend=COMPILE_BACKEND, fullgraph=True)`, jit.script fallback), not run eager. Import `_USE_COMPILE`/`COMPILE_BACKEND` from `lfr_simulate`.

Audit inherited flags (`orth_observe`, `orth_beta`, `joint`, `snr`) against the experiment's intent before launch, and state them in the run-table row. Process corollary: a user KILLING a background job is NOT approval to relaunch a modified variant — confirm the config change first.
- **effect-in-consuming-representation** — Express a new physical effect (friction) in the CONSUMING pipeline's representation, checked first (Python LPV-LFR simulate: M/C/K matrices + the LFR z/w Delta path for a static nonlinearity), not a convenient MATLAB ode45 wrapper. Fixed-parameter open-loop what-ifs are secondary and can mislead (a fixed, different-machine value is far from what the data would fit).
- **identify-the-missing-scalar** — When a known model has one unknown scalar and calibration data exists, identify it by least squares (`scale = <h, MF30>/<h, h>`); do not replace the model with a static-gain/RMS proxy that removes the frequency shaping.
- **fix-not-delivered-until-deployed** — A fix the user runs elsewhere (cluster) exists only locally until re-synced: say so prominently and give a one-line verify command (grep the removed line). On a returning complaint, establish WHICH copy ran before re-diagnosing. Uncommitted changes make git-based sync silently miss the fix.
- **no-scaffolding-in-experiment-scripts** — Keep operational hooks (SMOKE_TEST env modes, preflight gates, rehearsal switches) out of experiment scripts, and do not remove user-visible output (tqdm, prints) as "noise". Approval of a goal or a tool's value is not approval of the artifact; on hesitation ("not sure I like this"), remove without defending. For any new tool >~100 lines, show the skeleton first. STICKY: every gantry training/search script MUST print `[nf-probe] train nf-RMS / val nf-RMS` each epoch (reinstall the probe per chunk; plain `train_model` does not install it).
- **rule-out-bug-with-the-right-reference** — When a free-run/open-loop error looks anomalously large (e.g. e-05 where you expected e-07), rule out a model bug with the DIRECT control, not a mechanism-dependent discriminator. A true-x0 (oracle) free-run isolates the model+discretization floor; the gap to an encoder-x0 free-run is the SUBNET encoder-init error, not a bug (verified 2026-07-23: baseline true-x0 floor 3.79e-7 m = param_recovery's e-07, which free-runs from `state_traj[:1]`=true x0; the 1.58e-5 encoder-x0 floor was 97.6% encoder-init). Do NOT use "ARTBP should remove it" as the bug test: its outcome is ambiguous (ARTBP can WORSEN a variance-dominated drift on the marginal z=1 mode, D-120 caveat). ## Verification & testing
- **test-zero-mean-properly** — Separate the DESCRIPTIVE question ("is this recorded signal/correction zero-mean?", answerable on EXISTING data: compute the signal, run the tests) from the INFERENTIAL one ("does the system/baseline have a static DC deficiency in general?", which needs DC-exciting data because a U0=0 multisine is DC-blind). Answer the descriptive question asked on the data we have; state DC-blindness as a CAVEAT on the result, do NOT escalate to generating new excitation unless the user asks the inferential question. The correction the ANN must learn is defined on the training records, so the training distribution is the correct place to test it. To decide if a signal/residual/correction is zero-mean or DC-free, never use a `|mean|/std` (or `|mean|/rms`) ratio or eyeball "park vs ramp" — neither is a hypothesis test. Do: (1) classify stationarity FIRST (KPSS null=trend-stationary + ADF null=unit-root) — on a K=0 integrator axis the raw position mean is ill-posed (nonstationary), so test the stationary quantity (velocity, or the one-step model residual), and "deterministic park vs stochastic drift" IS the unit-root question; (2) test the mean with a HAC / Newey-West long-run-variance t-stat, because under autocorrelation (150 Hz ripple + slow trend) `std/sqrt(N)` is wildly optimistic and the true sample-mean variance is `2pi*S(0)/N` (spectral density at f=0); (3) the required correction is literally the baseline's one-step RESIDUAL, so "does the system demand a non-zero-mean correction" = the standard SysID residual test: zero-mean (HAC t) + whiteness (Ljung-Box); (4) two reframes that must accompany any verdict: a multisine with U0=0 carries ZERO information about the static/DC gain (a "zero-mean" finding is partly guaranteed by the DC-free experiment, not the physics — identifiability), and a nonlinear/LPV plant rectifies zero-mean input into a genuine 2nd-order Volterra DC, so "zero-mean input" never implies "zero-mean output". (5) MIRROR BLINDNESS in DC-excitation design: each waveform probes only its OWN DC mechanism. A U0=0 multisine is blind to STATIC-GAIN DC; a pure sustained/step input is blind to the AC-driven 2nd-order RECTIFICATION DC (it drives the plant to a nonlinear static equilibrium — no oscillation to rectify, so any resonator/MSD state relaxes to 0). At steady state qddot=0, so the mass matrix M — often the ONLY thing differing between two models — drops out of C*qdot+K*q=F; a static open-loop same-input test then confirms only "no static-gain difference" (frequently predetermined ~0 by that algebra), NEVER the full "system carries no DC the baseline lacks". The rectification DC that SURVIVES a truth-minus-baseline difference (here the MSD delta_a term) needs an AC component at the resonance to appear. To test BOTH mechanisms in one run, drive an offset PLUS an AC burst. Before calling a DC/excitation test "in line with the theory", name which DC mechanism the waveform actually excites and confirm it is the one the theory flags as real. Tools: statsmodels `kpss`, `adfuller`, `acorr_ljungbox`, HAC via `cov_type='HAC'`.
- **verify-nonlinear-mechanism-fully** — To attribute a measured effect to a specific nonlinear mechanism (quadratic / Volterra rectification), do three things or you may measure a look-alike: (1) excite the STATE the mechanism depends on and PROVE it moved (report its amplitude/RMS — a driven axis that barely reaches the state gives a false "negligible"; here only the Y drive moved delta_a, RMS 1.67e-5, vs ~1e-11 on X); (2) OBSERVE the channel where the nonlinear term physically lives (its home coordinate: the delta_a^2 term sits in the Theta inertia M(2,2), so read Theta, not the driven axis); (3) verify the expected SCALING (rectification DC ~ <state^2>, so it must track amplitude^2: measured B[Theta]=3.1e-10 matched <delta_a^2>=(1.67e-5)^2=2.8e-10 to ~10%). Matching magnitude AND scaling confirms the mechanism; a same-order number on a drive that does NOT excite the state is a DIFFERENT effect (here the L0 / mass-split static mass-matrix asymmetry), not the mechanism.
