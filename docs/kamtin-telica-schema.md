# Kamtin - Telica Data Schema

> **Access:** Raw data in `kamtin-data/Data Telica/` is blocked (`.claudeignore`).
> This file is the sole reference for structure, columns, file organisation,
> and the train/validation/test split.
> Verified against disk and Telica hardware documentation on 2026-07-03
> (decisions D-069, D-073, D-074).

---

## System

**Telica** - dual-gantry die-bonder system (ASMPT).
Two beam heads (Left/Right); per beam head two X-rails (GTRX1, GTRX2) and one Y-axis (GTRY).
The FP model covers **BHL** (Beam Head Left) only. BHR is parked during these campaigns
(constant setpoint, small holding currents).

## Parameter and controller files (`kamtin-data/`)

| File | Content | Status |
|------|---------|--------|
| `Telica.mat` | Machine parameters, FRF measurement (3x3 plant FRFs at 9 positions, `[cnt/dac]`), DatalogList | **AeroPro machine, not Telica** (`MachineType = "AeroProCoC"`). Its Filter1/Filter2 do NOT match the data (11-22x reconstruction error, D-069). Hardware constants coincide with the Telica values. |
| `Telica 1.mat` | Real Telica hardware constants: AmplifierGain 0.0020751953125 A/DAC (= 17/8192), EncoderResolution 9.765625e-10 m/cnt, MotorForceConst Kt_X 109 / Kt_Y 77.6 / Kt_Z 9.7 N/A, SamplingTime 5e-5 s | No controller section. |

| `dFeedbackControllersTelica_ba.mat` | Derived: num/den export of the above for scipy (`num_mat`, `den_mat`, `Ts`, `axis_names_char`). Generated by `scripts/gantry/real-data-verification/export_controllers_ba.m`. | Bit-exact vs MATLAB `filter(tfdata(zpk))` (diag_cl_correctness.py check 1). |

## Column Structure (`iter*.log` files)

Tab-separated. First row = header, subsequent rows = numeric data.

### Column naming convention

Raw header format: `<BeamHead>_<Axis>.<SignalType>:<ChannelIndex>`
The channel index (`:0.x`) is an internal ID; strip it when reading (as MATLAB does).
Dots are replaced with underscores in MATLAB structs -> `BHL_GTRX1_M0`.

### Beam heads

| Prefix | Meaning |
|--------|---------|
| `BHL`  | Beam Head Left (modelled) |
| `BHR`  | Beam Head Right (parked in these campaigns) |

### Axes

| Code    | Axis |
|---------|------|
| `GTRX1` | X-axis rail 1 |
| `GTRX2` | X-axis rail 2 |
| `GTRY`  | Y-axis |

### Signal types

| Suffix  | Meaning                                   | Raw unit | Conversion |
|---------|-------------------------------------------|----------|------------|
| `M0`    | Reference / setpoint position             | um       | x 1e-6 -> m |
| `M2`    | Tracking error (= M0 - actual position)   | um       | x 1e-6 -> m |
| `MF230` | **Feedback controller output** current    | A        | x Kt -> N |
| `MF30`  | **Total** current command (ff + feedback) | A        | x Kt -> N |

ILC feedforward current = `MF30 - MF230`. In `iter0` the feedforward is zero, so
`MF30 == MF230` exactly (bit-identical columns): iter0 is a pure-feedback run and
therefore an exact input/output pair of the feedback controller (M2 -> MF230).

Naming note: the "230 / 30" in `MF230`/`MF30` stems from old MATLAB comments
("230 Hz / 30 Hz filter"); it does NOT describe the semantics above, which were
established from the data (D-069) and confirmed by controller replay (D-074).

Timing note: the logged M2 and MF230 channels are not perfectly time-aligned;
MF230 lags K(M2) with a broad correlation maximum around 2.5 ms. A delay of that
size cannot exist inside the physical loop (it would destabilise the servo), so it
is a logging-path artefact (diag_cl_correctness.py check 4).

### Full column list (25 columns)

```
TimeStamp
BHL_GTRX1_M0    BHL_GTRX1_M2    BHL_GTRX1_MF230    BHL_GTRX1_MF30
BHL_GTRX2_M0    BHL_GTRX2_M2    BHL_GTRX2_MF230    BHL_GTRX2_MF30
BHL_GTRY_M0     BHL_GTRY_M2     BHL_GTRY_MF230     BHL_GTRY_MF30
BHR_GTRX1_M0    BHR_GTRX1_M2    BHR_GTRX1_MF230    BHR_GTRX1_MF30
BHR_GTRX2_M0    BHR_GTRX2_M2    BHR_GTRX2_MF230    BHR_GTRX2_MF30
BHR_GTRY_M0     BHR_GTRY_M2     BHR_GTRY_MF230     BHR_GTRY_MF30
```

`TimeStamp` values are host-side reception times and must never be used for
resampling (still-valid part of D-061).

## Iteration file meaning (`iter*.log`)

| File        | Meaning |
|-------------|---------|
| `iter0`     | Feedforward off - pure feedback only (exact controller I/O pair) |
| `iterETEL`  | Baseline: default ETEL feedforward (no ILC) |
| `iter1`-`iterN` | ILC iterations, feedforward improving each step (N = 8, some folders 10) |
| `iterTEST`  | Final feedforward generated by ML model (test folders only) |

Oddity: `train/xpos_-60_ypos120/` contains an extra `iter6_1.log` (redo of iter6).

`ml-feedforwards/` subfolder (`.txt` files): ILC update signals written to the
lookup table; not used for modelling.

## Folder structure and train/validation/test split

The `xpos_` / `ypos_` folder names encode the **start position in mm** (the
scheduling-relevant stage position). Each run moves 40 mm in X and 80 mm in Y
from that start position. **The split is by operating point** (the supervisor's
split; folders verified on disk 2026-07-03). All iterations inside one operating
point share the same reference trajectory and differ only in feedforward.

```
kamtin-data/Data Telica/
|
+-- 03 70mm XL/                      iter0..iter10 directly (single position, X-only 70 mm)
|
+-- 06 40 mm XL 80 mm YL/            the LPV dataset
    |
    +-- train/          11 operating points
    |     xpos_-60_ypos-40     xpos_-60_ypos120     xpos_-60_ypos-120    xpos_-60_ypos-200
    |     xpos_-135_ypos40     xpos_-135_ypos-40    xpos_-135_ypos-200
    |     xpos_-210_ypos40     xpos_-210_ypos120    xpos_-210_ypos-120   xpos_-210_ypos-200
    |     (each: iter0..iter8 + iterETEL; four folders also have iter9/iter10)
    |
    +-- validation/      2 operating points
    |     xpos_-135_ypos120    xpos_-210_ypos-40
    |     (each: iter0..iter8 + iterETEL)
    |
    +-- test/            2 operating points
          xpos_-135_ypos-120   xpos_-60_ypos40
          (each: iter0..iter8 + iterETEL + iterTEST; plus ml-feedforwards/)
```

Volumes (raw rows at 20 kHz; roughly half of each log is pre-motion standstill
that the loader trims):

| Split | Operating points | Logs | Raw rows | Raw duration |
|-------|------------------|------|----------|--------------|
| train | 11 | 110 | 1.99 M | 99.7 s |
| validation | 2 | 20 | 0.30 M | 15.1 s |
| test | 2 | 22 | 0.34 M | 17.1 s |

Grid coverage: xpos in {-60, -135, -210}, ypos in {-200, -120, -40, +40, +120}.
Both test points lie inside the training grid (interpolation).

## Unit conversions (confirmed from Telica 1.mat + data)

| Signal | Raw unit | Conversion | Result |
|--------|----------|------------|--------|
| M0, M2 | um | x 1e-6 | metres |
| MF30, MF230 | A | x Kt [N/A] | Newtons |

Motor force constants (`Telica 1.mat`, identical values in `Telica.mat`):
- `Kt_X = 109 N/A` (applies to GTRX1 and GTRX2)
- `Kt_Y = 77.6 N/A` (applies to GTRY)

**Native logging rate: 20,000 Hz** (= 1/SamplingTime; `SamplingFrequency = 20000`,
"The number of samples logged per second"). Confirmed empirically by the
controller-notch fingerprint (D-073): the LX1 notch appears at the same normalized
frequency in the log as in the 20 kHz controller design. The earlier 10 kHz
assumption (`FsHz = 1/(2*TsSec)`, D-061) is superseded; no resampling is performed
by the loader.

Note: the 481.882 factor in `runFDILCAllHostSwLog.m` line 326 is 1/AmplifierGain
(= 8192/17 DAC/A). It converts A -> DAC when **writing** the feedforward lookup
table. It does NOT apply when reading the logged MF30/MF230 signals (already in A).
