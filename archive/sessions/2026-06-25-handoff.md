## New session: Telica data — can our FP model fit it?

### Context

We now have real Telica ILC data (`kamtin-data/Data Telica/`, blocked via `.claudeignore`).  
Schema and folder structure: `docs/kamtin-telica-schema.md`.  
The data is position-scheduled (xpos/ypos folders = LPV scheduling variable).

**The question**: Is the Telica data compatible with our FP model structure, and is it worth attempting parameter recovery on it?

### Scope for this session

Start with **a single operating point** (one xpos/ypos folder, e.g. `train/xpos_-60_ypos-40/`).  
Do not attempt the full LPV dataset yet.

### Two parallel tracks — run at session start

**Track 1 — existing tooling: `train_param_recovery.py`**
- Understand what it does and whether it can be applied to Telica data as-is
- What inputs does it expect? Does the Telica data format match?
- What would "success" look like — what metric tells us the model fits?

**Track 2 — online research (spawn a research agent immediately)**
- Search for methods to assess whether a given model structure can describe a dataset
- Relevant keywords: model structure validation, goodness-of-fit, system identification validation, model falsification, output error method, simulation error
- What does the system identification literature recommend before committing to parameter estimation?
- Are there lightweight pre-checks (e.g. frequency response comparison, residual analysis) before running full param recovery?
- Report back: top 2-3 methods ranked by fit for our case (FP model, single operating point, ILC iteration data)

### Decision gate

After both tracks report:
- If the model structure is plausible: proceed to `train_param_recovery.py` on a single operating point
- If the structure is a poor fit: discuss what would need to change before the data is useful
