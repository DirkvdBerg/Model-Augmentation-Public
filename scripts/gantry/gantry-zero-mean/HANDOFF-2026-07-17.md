## The question
Jan's Theme A / gate G-A: does the with-MSD gantry system carry a static / non-zero-mean (DC)
component that the baseline lacks? If yes, the ANN is correctly learning a non-zero-mean
correction and the fix is model-side; if no, the DC the ANN learns comes from the estimator or
training (G-B / G-C), not the physics.

## SETTLED THIS SESSION (do not re-open)
1. **The recorded data cannot answer this.** The excitation is a multisine on 130-180 Hz with
   `U0 = 0` (no power at DC by design). It is STRUCTURALLY BLIND to a static/DC component
   (identifiability; Pintelon-Schoukens; methodology doc section 5). A "zero-mean" verdict on
   these records is partly guaranteed by the experiment, not the physics.
2. **Therefore testing the DC needs a SPECIFIC DC-exciting input.** Reusing the existing records
   for the DC question is wrong (this contradicted our own research and caused most of today's
   churn; see `dont-contradict-own-research`).
3. **The instrument is OPEN-LOOP, same input through both plants.** The closed-loop Simulink
   generator (`gtd_run_simulation`) cannot do it: it REJECTS DC disturbances (masks the static
   effect) and gives each plant a different input (not same-input). Open-loop with one identical
   DC-exciting input through both plants reveals a static difference unmasked. Same logic as v1d.
4. **Tooling: MATLAB.** The plant EOMs and parameters live in MATLAB; the user runs MATLAB. Do
   not build this in Python.

## SINGLE NEXT ACTION — implement `v1f_dc_excitation_openloop.m`
A drafted version was written this session but NOT saved (rejected mid-session; write it fresh).
Spec:
- **Setup**: reuse the v1d harness exactly (`v1d_openloop_same_input_msd.m` lines 45-107):
  `cfg = gtd_config('augmentation', true, 0.10)`; the two EOM handles `f_truth`
  (`gantrySystemExtended`, 8-state) and `f_base` (`gantrySystem`, 6-state); fixed-step RK4 at
  `cfg.ts`.
- **Excitation**: a smooth raised-cosine (jerk-limited) ramp over ~0.5 s up to a SUSTAINED
  constant logical force, applied to ONE axis at a time (X, then Theta, then Y). Sustained force
  is the DC content the multisine lacks; smooth onset avoids an abrupt jerk transient.
  Size the level to a small target so the K=0 position excursion stays in range:
  `F_X = 0.03 * (cg1+cg2)`, `F_Y = 0.03 * cy` (target terminal velocity ~0.03 m/s);
  `T_theta = 1e-3 * (kb1+kb2)` (target steady angle ~1e-3 rad). Run ~5 s (several tau;
  tau_X ~ 1.55 s, tau_Y ~ 1.01 s).
- **Read-out**: on X/Y (K=0 integrators) the terminal velocity `F/c`; on Theta the steady angle
  `torque/(kb1+kb2)`. Report per axis: truth steady value, baseline steady value, and the
  difference truth-minus-baseline over the final ~40% of the record.
- **Physics prediction (formula-level, `gantrySystemExtended.m`)**: truth and baseline share
  total mass (`mh_total = mh + ma`), damping and stiffness, and the MSD spring is UNPRELOADED
  (L0 enters only the mass matrix, never as a force). So static response is IDENTICAL:
  difference at the numerical floor CONFIRMS the system carries no DC the baseline lacks
  (G-A refuted properly, on DC-exciting data). A resolved nonzero difference that GROWS with the
  driven level is a real static MSD effect (support for Jan). Either outcome is defensible.
- **Extension (folds in the old operating-point question)**: repeat from several initial Y
  (Y0 = -0.30, 0, +0.10, +0.30) to see whether any static difference is operating-point
  dependent. This replaces the old "V1 vs T1" thread cleanly.
- **Output**: figures -> `figures/v1f_<axis>_*.png`, results -> `data/v1f_results.mat`, console
  -> `data/v1f_console.txt` (diary), matching the v1d convention. Stop for user review after the
  first run; do not chain into training or Python.
